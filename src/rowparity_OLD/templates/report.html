Fingerprints are computed with hashlib.blake2b over a type-aware canonical form of each row - floats quantized to tolerance, decimals stripped of trailing zeros, timestamps normalized to UTC, so an int32 from one engine and an int64 from another still fingerprint identically when the value is the same. Two tables are equivalent exactly when their multisets of fingerprints match; row order never enters into it. This report reads directly off the same rowparity_run_summary / rowparity_run_diffs tables any query engine can query - nothing here is computed specially for display.
